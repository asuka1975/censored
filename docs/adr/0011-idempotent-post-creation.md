# ADR-0011: 投稿の作成の冪等性を、作者と要求の識別子の一意制約で実現する

- Status: Proposed
- Date: 2026-11-03
- Deciders: asuka1975

## 背景

投稿の作成は、再送され得る書き込みである(NFR-REL-3)。ブラウザの通信が途中で切れると、利用者の画面は結果を知らないまま同じ要求を送り直す。送り直しで投稿が増えてはならない。[Issue #14](https://github.com/asuka1975/censored/issues/14) の受け入れ条件は、同じ要求の再送は投稿を 1 件のままにして同じ投稿を返すこと、同じ要求の識別子で別の本文を送ると拒否すること、同時に届く同じ要求でも 1 件になることを求めている。

ユースケースが「要求の識別子で投稿を探す → 無ければ保存する」と 2 つの操作に分けると、同時に届く 2 つの要求が、どちらも「無い」と判断して、2 件保存できる。純粋な関数やユースケースの書き方では防げない。保存先が原子的に判断する必要がある。

データストアは未決定である(`docs/architecture/README.md`)。契約は特定の DB に依存してはならない。ただし、どの DB にも「一意制約に違反する挿入は失敗する」か、それに相当する原子的な操作がある、というのは、広く知られた性質である。

検証していないこと: 実際の DB で、この契約がどの程度の性能で実装できるかは、確かめていない。データストアを決める ADR で確かめる。

## 決定

要求の識別子は、利用者側(ブラウザ)が付ける UUID とする。投稿の保存は、`insertPostOnce :: UserId -> RequestId -> Post -> IO (Maybe Post)` の 1 つの操作にする。(作者, 要求の識別子)の組が未登録のときだけ、投稿を保存して `Nothing` を返す。登録済みなら、何も保存せずに、保存されていた投稿を返す。この判断と保存は、同時に届く別の呼び出しに対して原子的でなければならない。実装は、(作者, 要求の識別子)の一意制約など、保存先の原子的な機能で実現する。

ユースケースは、返された既存の投稿が、今回の要求と同じ内容(本文と返信先)なら、その投稿を返す。違えば、要求の識別子の再利用として拒否する。投稿は不変なので、この比較は保存後に行っても競合しない。

要求の識別子は作者ごとに区別する。別の利用者が同じ識別子を使っても、互いに干渉しない。他の利用者の識別子を推測しても、その利用者の投稿は見えない。

## 検討した代替案

### 案 A(採用): 作者と要求の識別子の組で、「未登録のときだけ保存」を 1 つの操作にする

利点: 並行して届く要求で投稿が 2 件できないことを、Port の形で強制する。ユースケースは読み書きを分けて呼べない。比較の対象(保存済みの投稿)が不変なので、比較に競合が無い。
欠点: 保存先に、(作者, 要求の識別子)の一意性を持たせる必要がある。要求の識別子を、投稿とは別に保存し続ける(保持期間は未定)。

### 案 B: 投稿の内容(本文と返信先)のハッシュで、重複を判定する

利点: 利用者側が要求の識別子を付けなくてよい。
欠点: 同じ本文を、意図して 2 回投稿する操作(「ありがとう」を別々の相手に返信するなど)と、再送を区別できない。時間の窓を決める必要があり、恣意的になる。
**却下理由:** 利用者の意図を取り違える。意図の区別は、利用者側が要求の識別子を付けるのが確実である。

### 案 C: ユースケースが「探す」と「保存する」を別々に呼び、保存の失敗で重複を検出する

利点: Port が単純で、DB の一般的な使い方に近い。
欠点: 保存の失敗が「重複」か「その他の障害」かを、Port の利用側が区別する必要がある。区別を誤ると、障害を重複として握りつぶす。
**却下理由:** 失敗の意味の区別を利用者の側に押し付け、誤用しやすい。案 A は、結果を型(`Maybe Post`)で返す。

## 結果

- 再送で投稿が増えない。同時に届く同じ要求でも 1 件になる。
- infra は、(作者, 要求の識別子)の一意性を保存先に持たせる。要求の識別子の保持期間を決める必要がある(未決。データストアの ADR で決める)。
- 要求の識別子を再利用して別の内容を送ると拒否される。利用者側(ブラウザ)は、要求ごとに新しい UUID を作る必要がある。
- 別の利用者の要求の識別子とは干渉しないので、推測による攻撃面は増えない。

## 再検討の条件

- データストアの ADR で、この契約が実装できない、または性能の目標を満たさないと分かったとき。
- 投稿の作成以外(いいね、フォローなど)にも、同じ冪等性が必要になったとき。共通の仕組みにするかを検討する。
- 要求の識別子を保持し続ける費用が、無視できなくなったとき。
