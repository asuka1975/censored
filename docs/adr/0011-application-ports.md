# ADR-0011: application の Port を IO の関数のレコードにし、候補の組の更新を 1 つの原子的な操作にする

- Status: Proposed
- Date: 2026-11-03
- Deciders: asuka1975

## 背景

[Issue #2](https://github.com/asuka1975/censored/issues/2) の投稿の流れは、AI を外部依存(Port)の背後に置く。`docs/conventions/01-directory-structure.md` は、Port を application に置き、infra が実装すると定めている。Port の形(関数のレコードか、型クラスか)は、まだ決まっていない。

候補の組には「選べるのは 1 回だけ」「同じ候補を選ぶ再送は同じ投稿を返す」という条件がある(NFR-REL-3)。domain の `selectCandidate` は純粋関数で、1 つの組の状態遷移としては正しい。しかし、application が「組を読む → `selectCandidate` を呼ぶ → 結果を書く」を別々の Port 操作として呼ぶと、同時に届く 2 つの選択が、どちらも `Open` の組を読み、別々の識別子の投稿を 2 件作れる。これは PR #12 の NFR レビューが指摘した点で、domain の純粋関数では防げない。投稿の保存と組の更新が別の操作だと、片方だけが成功して、組は投稿済みなのに投稿が無い状態もあり得る。

データストアは未決定である(`docs/architecture/README.md`)。Port は特定の DB に依存してはならない。

検証していないこと: 下の決定の形が、実際の DB(行ロック、条件付き更新と再試行)で効率よく実装できるかは、確かめていない。

## 決定

Port は `IO` を返す関数のレコードとして application に置く(`CandidateGenerator`、`IdGenerator`、`Store`)。ユースケースは、それらをまとめた `Env` を受け取る関数にする。

候補の組の更新は、読み出しと書き込みを別の操作にせず、1 つの操作 `updateCandidateSet :: CandidateSetId -> (CandidateSet -> Update a) -> IO (Maybe a)` にする。渡す関数は純粋で、更新後の組、新しく作る投稿、呼び出し元に返す値を返す。実装は、その組の読み出しから書き込み(投稿の保存を含む)までを、同じ組への他の更新と直列にする。組が無ければ `Nothing` を返す。渡した関数は複数回呼ばれ得る(楽観的な再試行を実装が選ぶ場合)ので、副作用を持てない。

他人の組への操作は、存在しない組と同じ結果(`NotFound`)にする。組の存在を推測できる応答の差を作らない。

## 検討した代替案

### 案 A(採用): IO の関数のレコード + 原子的な更新の操作

利点: 同時に届く選択で投稿が 2 件できないことを、Port の形で強制する。ユースケースが読み書きを分けて呼べないので、誤用できない。更新の関数は純粋なので、テストはフェイクに状態を持たせるだけで足りる。追加の依存が無い。
欠点: infra は「関数を受け取る更新」を DB のトランザクションに対応させる必要がある。

### 案 B: 読み出しと保存を別の操作にし、保存にバージョンを渡す(楽観ロック)

利点: DB のアクセスの形として一般的で、実装の自由度が高い。
欠点: 競合時の再試行と、投稿と組の保存の原子性を、すべてのユースケースが自分で書く。
**却下理由:** 原子性が型で強制されず、書き方を誤ると投稿が 2 件できる。誤りがテストに現れにくい(単一スレッドでは起きない)。

### 案 C: mtl 風の型クラスで、ユースケースを多相にする

利点: テストで `IO` 以外のモナドを使える。
欠点: `mtl` か `transformers` への依存と、抽象の層が増える。いまのテストは `IO` のフェイクで足りる。
**却下理由:** 必要が示されていない。必要になったときに、Port のレコードを型クラスに置き換えるのは、ユースケースの型の変更だけで済む。

## 結果

- 並行して届く選択で、投稿が 1 件に保たれることを、Port の契約として infra に課せる。
- 他人の組と存在しない組の区別が、利用者に見えなくなる。サポートの調査では、サーバのログで区別する必要がある(ログに本文を出さない。NFR-PRIV-1)。
- 更新に渡す関数は複数回呼ばれ得るので、純粋でなければならない。型は純粋さを保証するが、`unsafePerformIO` で破る実装を型は防がない(HLint が禁止している)。
- 候補の生成に使う Port(`CandidateGenerator`)のタイムアウトと再試行の方針は、この ADR で決めない。実装する infra で決める(NFR-REL-2)。

## 再検討の条件

- データストアの ADR で、この形のトランザクションが実装できない、または性能の目標を満たさないと分かったとき。
- 更新が複数の組や、組以外の集合(タイムラインの配信など)を 1 つのトランザクションにまたぐ必要が出たとき。
- `IO` 以外のモナドでユースケースを動かす必要が、テスト以外で出たとき。
