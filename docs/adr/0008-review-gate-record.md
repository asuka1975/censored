# ADR-0008: レビューゲートの記録方式

- Status: Accepted
- Date: 2026-11-02
- Deciders: asuka1975(追認)

## 背景

非機能要件とテスト品質には、機械で判定できない項目がある。これらを AI のレビュアーが判定するとして、「レビューを実行した」ことを CI でどう確かめるかを決める必要がある。

## 決定

レビュアーは Claude Code のサブエージェントとして別のコンテキストで実行し、判定を PR 本文に `<!-- gate:<名前> sha=<HEAD> verdict=<pass|fail> reviewer=<名前> -->` の形で記録する。`check-pr` は記録の存在、HEAD との一致、`pass` であることを検証する。最終的な保証は人間の承認が担う。

本文の編集で再検査するため、`check-pr` は `edited` で起動する専用のワークフロー `pr-policy` で実行する。ビルドとテストのワークフローには `edited` を足さない。編集のたびに重いジョブが走るのを `if` で飛ばすと、スキップが必須チェックの合格として扱われ、失敗したジョブが本文の編集だけで合格に変わってしまう。

## 検討した代替案

### 案 A: PR 本文への記録 + 人間の承認(採用)

API キーや追加のコストなしに始められる。古いコミットへの記録は機械的に無効にできる。欠点は、**記録を手で書けば CI を通せること。** 文字列であり署名ではない。防御は人間の承認と CODEOWNERS に依存する。

### 案 B: CI 上でレビュアーを実行(claude-code-action など)

作成者が結果を偽造できず、CI の結果として独立性が保たれる。**却下理由:** API キーの管理とコストが発生し、外部からの PR で秘密情報を扱う問題の整理が必要になる。リポジトリの公開前に解決する必要はない。将来の移行先として最有力である。

### 案 C: レビュー結果をファイルとしてコミット

履歴に残る。**却下理由:** レビューの結果をコミットすると HEAD が変わるので、記録の対象と一致させられない。

### 案 D: 機械ゲートのみで AI レビューなし

単純である。**却下理由:** 認可の欠落のような「差分に現れないもの」を検出できない。

## 結果

- リベースのたびに再レビューが必要になる。基準が変われば判定の前提も変わるので許容する。
- 一人で開発する間は、作成者と承認者が同じ人間になる。承認の独立性はない。GitHub の設定では自分の PR を承認できないので、運用を決める必要がある。

## 再検討の条件

- 外部からの貢献を受け入れ始めたら(案 B に移行する)。
- 記録が実態と一致しない事例が 1 件でも見つかったら。
