# ADR-0007: バックエンドとフロントエンドの API 契約

- Status: Accepted
- Date: 2026-11-02
- Deciders: asuka1975

## 背景

言語が異なるので、型をコンパイラで共有できない。JSON の表現が食い違っても両方のテストは通り、本番で初めて失敗する。この構成で最も起きやすい事故である。

候補のうち `purescript-bridge` 0.15.0.0 は Hackage に存在し PureScript 0.15 に対応するとされるが、**本構成での動作は未検証である。**

## 決定

実装の選択にかかわらず、次を契約の方針とする。

1. API の型の正本はバックエンド(`censored-contract`)に置く。
2. 代表値の JSON を `contract/fixtures/` に固定する。バックエンドのテストが生成して一致を検証し、フロントエンドのテストがデコードして検証する。
3. `contract/` の生成物はコミットし、CI の `make contract-check` で、未追跡のファイルを含めて不一致を検出する。
4. 破壊的な変更は `contract/` の差分としてレビューで見える。

PureScript の型の生成方法は、最初のエンドポイントを実装するときに検証して別途決定する。第一候補は servant + `purescript-bridge`。

## 検討した代替案

### 案 A: バックエンドを正本 + fixture による両側の検証(採用)

生成の手段に依存せず、表現の不一致を検出できる。欠点は fixture の保守と、代表値にない形の不一致は検出できないこと。

### 案 B: OpenAPI を正本に手で書く

言語に中立。**却下理由:** PureScript 向けの成熟した生成器が見当たらず、手で書いた仕様と実装の乖離を別途検査する必要が生じる。

### 案 C: 型を両言語で手書きする

依存が増えない。**却下理由:** 乖離を検出できない。fixture で検出はできるが、書く量が増えるので生成できるなら生成する。

## 結果

- 最初のエンドポイントの実装時に、この ADR の未決定部分を決める必要がある。
- テストが `contract/` に書き出すので、テストの実行で差分が生じることがある。意図した変更なら fixture をコミットする。

## 再検討の条件

- `purescript-bridge` が GHC 9.10.3 でビルドできない、または生成コードが `--strict` を通らないことが分かったら。
- 外部に API を公開することになったら(バージョニングの方針を別途定める)。
