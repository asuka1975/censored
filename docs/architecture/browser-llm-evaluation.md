# ブラウザ内 LLM の評価の手順

[ADR-0012](../adr/0012-browser-llm-runtime.md) の計測の手順と、結果の記録。ランタイムとモデルを決めるための、人間が自分の端末で実行できる手順を書く([Issue #16](https://github.com/asuka1975/censored/issues/16))。

**結果は途中である。** 作成した環境では、モデルの置き場(`huggingface.co`、`cdn-lfs.huggingface.co`)と `cdn.jsdelivr.net` へ接続できず(ネットワーク方針が 403 で拒否)、GPU も無いため、計測できなかった。計測の道具は [`tools/llm-bench/`](../../tools/llm-bench/) に用意し、人間が自分の端末で動かした([計測の手順](#計測の手順))。2026-11-04 に、1 台のデスクトップの **WASM の経路だけ**を、#1、#4、#5、#6 で測った。#2 と #3 は実行できなかった。WebGPU の経路とスマートフォンは未計測である。結果は [結果](#結果) に書いた。

## 評価する構成

| # | ランタイム | モデル(量子化) | 経路 | 備考 |
| --- | --- | --- | --- | --- |
| 1 | transformers.js | Qwen3-0.6B(ONNX、q4) | WebGPU、WASM | 小さいモデルの基準 |
| 2 | transformers.js | Qwen3-1.7B(ONNX、q4) | WebGPU、WASM | |
| 3 | transformers.js | LFM3-1.7B(ONNX、q4) | WebGPU、WASM | #2 と同じ大きさの比較 |
| 4 | wllama | Qwen3-0.6B(GGUF、Q4_K_M) | WebGPU、WASM | |
| 5 | wllama | Qwen3-1.7B(GGUF、Q4_K_M) | WebGPU、WASM | |
| 6 | wllama | LFM3-1.7B(GGUF、Q4_K_M) | WebGPU、WASM | llama.cpp と wllama が LFM3 に対応するか未確認。GGUF が無い、または動かなければ、動かなかったと記録して省く |

モデルの選び方:

- 比べるモデルは Qwen3 と LFM3(人間の指示、2026-11-04)。Gemma は外した。
- Qwen3 は、公式の README が Apache 2.0 と書く。小型版(0.6B、1.7B)を使う。
- LFM3 は、Liquid の公式リポジトリ(cookbook)に `LFM3-1.7B` が出てくる。transformers.js の対応モデルに載る。`LFM3-1.7B` が日本語に対応することは、人間が確認した(2026-11-04)。ライセンスの条件は、確かめていない。**使う前に、人間が確認する。**
- ONNX と GGUF の配布の有無と、実際の大きさは、確かめていない。見つからないモデルは、別の同程度のモデルに替えて、記録する。
- WebLLM は、WebGPU でしか動かないので、基盤の候補にも、計測の対象にも含めない。

## 計測の手順

構成 1 つと経路 1 つを、ブラウザのページ 1 枚で測る。ページが時間、ダウンロード量、出力の判定を自動で記録する。人間が行うのは、サーバーの起動、キャッシュの消去、メモリの読み取り、採点、結果を返すことである。

### 準備

- Node.js 22 以上。リポジトリの依存の導入は要らない(ライブラリは版を固定して CDN から取る。transformers.js 4.3.2、wllama 3.8.1)。
- Chrome か Edge(WebGPU の経路は 113 以降)。`huggingface.co`、`cdn-lfs.huggingface.co`、`cdn.jsdelivr.net` に接続できること。
- 取得先のモデルの名前は、**#1 以外は推測である**。最初に、次の表の名前が `huggingface.co` に実在するか確かめる。無ければ、似たモデルを探して `repo=`(必要なら `file=`)で差し替え、使った名前を結果に書く。

| # | 既定の取得先 | 確認 |
| --- | --- | --- |
| 1 | `onnx-community/Qwen3-0.6B-ONNX` | transformers.js の例にある名前。存在は未確認 |
| 2 | `onnx-community/Qwen3-1.7B-ONNX` | 推測 |
| 3 | `onnx-community/LFM3-1.7B-ONNX` | 推測。無ければ Liquid AI の公式の取得先を探す |
| 4 | `unsloth/Qwen3-0.6B-GGUF`(Q4_K_M) | 推測 |
| 5 | `unsloth/Qwen3-1.7B-GGUF`(Q4_K_M) | 推測 |
| 6 | `LiquidAI/LFM3-1.7B-GGUF`(Q4_K_M) | 推測。llama.cpp が LFM3 に対応していないと、読み込みで失敗する(失敗も結果である) |

### GitHub Pages で測る

手元のサーバーとブランチの取得が要らない。`gh-pages` ブランチに、計測ページの静的ファイルだけを置いて公開する。`main` へのマージは要らない。HTTPS なので WebGPU が使え、スマートフォンでは最も手軽である。

- URL: `https://asuka1975.github.io/censored/?config=3&backend=webgpu&cache=cold`(Settings → Pages で「Deploy from a branch」、`gh-pages` の `/ (root)` を指定した場合)。
- 公開と更新: `tools/llm-bench/publish-pages.sh`。HEAD にコミットされた版を公開する。`PAGES_DRY_RUN=1` を付けると、公開する中身の表示だけをする。
- **Pages では測れないもの。** ヘッダーを設定できないので、cross-origin isolation にならない。wllama のマルチスレッドと、`performance.measureUserAgentSpecificMemory` は使えない。それらはローカルのサーバー(下の手順)で測る。
- 保存先は `asuka1975.github.io` のオリジンで、同じ利用者の他の Pages サイトと共有される。「Clear site data」は他のサイトのデータも消すので、計測用のブラウザプロファイルを使う。
- Pages はファイルを 10 分程度キャッシュする。更新後はハードリロードする。
- 公開されている。誰でも開け、各自のブラウザでモデルをダウンロードする。計測が終わったら `gh-pages` ブランチを削除して、公開を止める。

### 端末の診断

モデルを読み込む前に失敗する端末(スマートフォンなど)では、診断ページが、読み込みの前提の能力を 1 つずつ試して、どこで失敗するかを残す。ライブラリは使わない。

- URL: `https://asuka1975.github.io/censored/probe.html`(ローカルでは `http://localhost:8080/probe.html`)。
- 試すもの: 環境(`jspi`、`memory64`、`crossOriginIsolated`)、ストレージの見積り(使用量と上限)、取得先への接続(API と、ファイルの先頭 1 MiB)、モジュールのワーカー、OPFS(ワーカーで 64、256、512 MiB を書く)、`WebAssembly.Memory`(256、512、1024、2048 MiB を、試行ごとにワーカーで確保する)、WebGPU(アダプターとバッファの確保)。
- 大きい方から失敗したときは、`reachedMiB`(通った大きさ)と `failedAtMiB`(最初に失敗した大きさ)と `error` が出る。大きさは `opfs_mib=64,256`、`mem_mib=256,512`、`gpu_mib=256` で変えられる。
- 「結果をコピー」を押して、貼る。

### 1 つの構成を測る(ローカルのサーバー)

1. サーバーを起動する。`--isolation` は後述。

   ```bash
   node tools/llm-bench/serve.mjs --port 8080
   ```

2. **冷間(初回)の測定。** 開発者ツールの Application の Storage で「Clear site data」を押す。次の URL を開いて「計測を始める」を押す。`config` は上の表の #、`backend` は `webgpu` か `wasm`。

   ```text
   http://localhost:8080/?config=1&backend=wasm&cache=cold
   ```

   14 件すべてを 1 回ずつ生成する。終わるまで待つ(WASM の大きいモデルは数十分かかりうる)。生成中に Chrome のタスクマネージャー(Shift+Esc)でこのタブの「メモリ フットプリント」を読み、「タスクマネージャーのタブのメモリ」に入れる。出力の採点は任意(下の「採点」を見る)。
3. 「全体を JSON で保存」を押し、ファイルを残す。「要約をコピー」で、要約をコピーする。
4. **温間(2 回目)の測定。** キャッシュを残したまま、次の URL を開いて同じ操作をする。2 回目の読み込み時間と、生成の時間の中央値(3 トピック × 3 回 = 9 回)が取れる。

   ```text
   http://localhost:8080/?config=1&backend=wasm&cache=warm&topics=1,3,13&reps=3
   ```

5. 手順 2〜4 を、ほかの構成と経路で繰り返す。

全部を測れなくてよい。先に #1 と #3(最も小さいモデルと LFM3)を WebGPU と WASM で測り、桁を見る。次に #2、そして wllama(#4〜#6)。最後に、残った候補を中程度のスマートフォンで測る。

### 注意

- **冷間が冷間でないとき。** 要約の `load.storageDeltaBytes` が 0 に近ければ、キャッシュが残っていた。「Clear site data」で消えなかったので、新しいプロファイルで測り直す。
- **WebGPU の経路。** 使えない端末では、ページは「アダプターを取得できない」と表示して止まる。WASM に黙って落とすことはしない。
- **wllama のマルチスレッド。** `--isolation require-corp`(または `credentialless`)でサーバーを起動した測定と、起動しない測定の両方を取る。結果の `env.crossOriginIsolated` で見分けられる。ヘッダーを付けると、CDN からの読み込みが拒否されて失敗することがある。失敗したら、そのまま報告する。GitHub Pages では測れない。
- **生成は貪欲法(temperature=0)。** 再現するため。繰り返しの出力で無効が増えたら、サンプリングを足して測り直し、設定を書く(例: `temperature=0.7&top_p=0.8&top_k=20`。Qwen3 のモデルカードの推奨値を覚えているものだが、ここでは確かめていない。LFM3 の推奨値はモデルカードで確かめる)。
- **量子化の指定。** transformers.js の `dtype` は q4 が既定。WebGPU で `shader-f16` が使える端末(結果の `env.adapter.shaderF16`)では、`dtype=q4f16` も測る価値がある。wllama は `quant=Q4_K_M` が既定。
- **Qwen3 の思考。** Qwen3 の構成は、利用者の発言の末尾に `/no_think` を付けて思考を止める。LFM3 には付けない。それでも `<think>` が出たときは取り除いて判定し、`hadThinking` に記録する。
- **チャットテンプレートが無い GGUF。** #6 のように `createChatCompletion` が落ちるときは、`prompt_format=chatml` を付けて測り直せる(wllama の構成だけ)。LFM3 の本来の形式を確かめるまで、この結果は参考値として扱う。
- **キャッシュに保存しない。** `use_cache=0` を付けると、モデルをブラウザのストレージに保存せず、メモリだけで読み込む(wllama は `useCache: false`、transformers.js は `env.useBrowserCache` と `env.useWasmCache` を切る)。保存の失敗を切り分ける実験で、毎回ダウンロードし直すので、温間の測定には使えない。結果の `load.storageQuotaBytes` に、ブラウザが報告するストレージの上限が出る。
- **スマートフォン。** GitHub Pages で開く(上の節)。Wi-Fi に接続し、測定の間は画面を点けたままにする。道具は画面を点けたままにする要求(Screen Wake Lock)を出すが、拒否されることがある。結果の `env.wakeLock` と、`visibility`(ページが隠れた回数と秒数)で確かめられる。最も小さい構成(#1 か #4)で動くことを先に確かめてから、大きい構成に進む。読み込みが途中で失敗したときは、結果の `engine.lastFile` が、直前にダウンロードしていたファイルを示す(transformers.js のみ)。

### 道具のテストと削除

道具は、計測が終わったら削除する使い捨てである。**CI には組み込まない**(`make check` にも `make test-gates` にも入れていない)。判定や集計の誤りは「有効な出力」の数字を歪めるので、道具を変えたときは手元で実行する。

```bash
node --test tools/llm-bench/test/*.test.mjs
```

計測の結果を ADR-0012 に反映したら、`tools/llm-bench/` と `gh-pages` ブランチを削除する。

### 結果を返す

- 構成と経路ごとに「要約をコピー」した JSON を、そのまま貼る(1〜2 KB)。端末の説明(CPU、GPU、メモリ、OS、回線の速さ)を一言添える。
- 全体の JSON(各出力を含む)は、候補の質を見る必要がある構成だけ、Issue のコメントか、リポジトリの外に置いた場所に貼る。このリポジトリには入れない。

### 採点

ページの表に、出力ごとの 4 つの観点を 1〜5 で入れられる。入れた値は要約の平均に反映される。全構成の全件を採点するのは重いので、有効な出力が 12 件以上あった構成だけを採点してよい。「攻撃的な語が残る可能性」の印は、既知の罵倒語が候補に含まれるかを見ただけの目安で、採点の代わりにはならない。

## プロンプトの草案

実装(#15)で見直す草案。計測では、すべての構成に同じプロンプトを使う。

```text
あなたは、投稿を穏当な日本語に整えるアシスタントです。
利用者が言いたいこと(トピック)を受け取り、同じ主張の核を保ったまま、攻撃的な言葉や人格への攻撃を避けた、短い投稿文を 3 つ作ります。
- 各投稿は 140 文字以内にする。
- 3 つの投稿は、言い回しを変える。
- 罵倒、差別、個人への攻撃は書かない。
- 返信先の投稿が与えられたときは、その内容に応える投稿にする。
- 出力は、文字列 3 つの JSON の配列だけにする。
```

## 計測の方法

1 つの構成と 1 つの経路ごとに、次を記録する。自動の項目はページが記録し、手動の項目は人間が入れる。

| 項目 | 方法 |
| --- | --- |
| 端末 | 自動(ブラウザの版、論理コア数、`navigator.gpu` の有無、アダプターの情報、cross-origin isolation の有無)。CPU、GPU、メモリ、OS は手動でメモに書く |
| ダウンロードの大きさ | 自動。ランタイムが報告する転送量(`load.downloadedBytes`、`totalBytes`)と、ストレージの使用量の増分(`load.storageDeltaBytes`) |
| 初回の読み込み時間 | 自動。`cache=cold` のとき、読み込みを始めてから生成できる状態になるまで(`load.loadSeconds`)。回線の速さは手動でメモに書く |
| 2 回目以降の読み込み時間 | 自動。`cache=warm` のとき、同じ時間 |
| 生成の時間 | 自動。最初のトークンまで(`summary.medianTtftSeconds`)と、3 つの候補を得るまで(`summary.medianTotalSeconds`)の中央値。最初の 1 回(シェーダーのコンパイルを含みうる)は `summary.firstRunSeconds` に別に出し、中央値に入れない。毎秒のトークン数は `summary.medianTokensPerSecond`(wllama は 1 チャンクを 1 トークンとみなす) |
| メモリ | 手動。ブラウザのタスクマネージャーで、生成中のタブのメモリ(MB)を読む。ページが取れる値(`memory.*`)は JavaScript のヒープなどに限られ、GPU のメモリを含まないので、代わりにならない |
| 有効な出力の割合 | 自動。14 件のうち、JSON の配列として解釈でき、空でない文字列がちょうど 3 つで、各 140 書記素以内だった件数(`summary.validTopics`)。ICU 相当の `Intl.Segmenter` で数える |
| 候補の質 | 人間が採点する(上の「採点」)。出力そのものも記録する |

端末は、少なくとも次の 3 種類を測る。

1. WebGPU を使える、GPU のある端末(デスクトップ)
2. WebGPU を使えない、または使わない、CPU だけの端末(WASM の経路)
3. 利用者の想定に近い、中程度のスマートフォン

## 候補の質の採点

各出力(3 つの候補)を、人間が 1〜5 で採点する。

| 観点 | 5 の基準 | 1 の基準 |
| --- | --- | --- |
| 穏当さ | 攻撃的な言葉も、人格への攻撃も無い | 罵倒がそのまま残る |
| 意味の保持 | トピックの主張の核が残っている | 別の話になっている |
| 日本語の自然さ | そのまま投稿できる | 文法が崩れている、意味が通らない |
| 3 つの違い | 言い回しが明確に違う | ほぼ同じ文 |

返信(#13、#14)は、返信先の投稿に応える内容かも見る。

表の読み方と、足りないところ:

- 3 候補の時間は、最初の 1 回を除く 13 回の中央値。貪欲法(temperature=0)、`reps=1`。
- `cache` を指定しなかった。ダウンロード量とストレージの増分が一致する(例: #4 は 397 MB と 397 MB)ので、4 件ともキャッシュが空の状態からの読み込みとみられるが、確かではない。回線の速さは記録していない。2 回目の読み込みは未計測。
- WASM は単一スレッド(wllama は `threads: 1` を報告)。transformers.js のスレッド数は、記録に無い。
- メモリ(タスクマネージャーの値)と、候補の質の採点は、入れていない。
- 「有効な出力」は、形式が合うかだけを見る。内容の良し悪しを表さない(下の観察を見る)。
- #2(transformers.js、Qwen3-1.7B の ONNX q4、WASM)は、読み込みで `RangeError: The ArrayBuffer/ArrayBufferView size exceeds the supported range.` で失敗した。モデルのファイルが、WASM(32 ビットのメモリ)で確保できる大きさを超えたとみられる。ダウンロード量は記録に無く、確かめていない。WebGPU の経路は未試行。
- #3(transformers.js、LFM3-1.7B の ONNX q4、WASM)は、`Can't create a session. ERROR_CODE: 9, ERROR_MESSAGE: Could not find an implementation for GatherBlockQuantized(1) node with name '/model/embed_tokens/Gather_Quant'` で失敗した。モデルの埋め込み層が 4 ビット量子化の演算(GatherBlockQuantized)を使い、WASM の実行環境(onnxruntime-web)にその実装が無い、という読みになる。取得先 `onnx-community/LFM3-1.7B-ONNX` は実在し、セッションの作成までは進んだ。WebGPU の経路と、別の量子化(`dtype=q8`)は未試行。
- #3 を iPhone(端末 B)の WebGPU で測ったところ、ダウンロードが 470 MB / 1315 MB(36%)で止まり、1018 秒後に `TypeError: Load failed` で失敗した(約 0.46 MB/s。回線はモバイル回線)。これは Safari の fetch がネットワークの層で失敗したときの一般的な文面で、ページは生きていた。原因は特定できていない。回線の断や遅さ、画面のロックやアプリの切り替えによるダウンロードの中断などが考えられるが、確かめていない。この測定の道具には、画面を点けたままにする処理と、ページが隠れた回数と時間の記録が無かった。LFM3 の ONNX q4 の合計は、ランタイムの報告で 1315 MB。この測定は、LFM3 が WebGPU の実行環境で動くか(#3 の WASM の失敗は演算の未実装だった)の答えにならない。デスクトップの WebGPU で測る。
- #4 を iPhone(端末 B)の WASM で測ったところ、20.4 秒後に `UnknownError: The operation failed for an unknown transient reason (e.g. out of memory).` で読み込みに失敗した。ダウンロードのバイト数は 0。この測定では、画面を点けたままにする要求が取れ(`wakeLock: acquired`)、ページが隠れた回数は 0 だった。したがって、前回の #3(`Load failed`)の原因の候補だった画面ロックやアプリの切り替えは、今回の失敗の原因ではない。
- 保存を切る指定(`use_cache=0`)で #4 を測り直しても、同じ失敗が出た(2.1 秒後、ダウンロードは 0 バイト、`UnknownError` の同じ文面。操作の直後に失敗した)。**「モデルをストレージに保存する段階で失敗している」という見立ては、支持されなかった。** この文面は、WebIDL が `UnknownError` に定めた汎用の説明で、どの API が投げても同じである。ストレージ層の文面とは言えない(前の版で、そう書いたのは誤りだった)。
- このときブラウザが報告したストレージの上限(`storageQuotaBytes`)は 1,048,576,000 バイト(約 1 GB)だった。1 GB を超えるモデル(#5 の 1107 MB、#3 の 1315 MB)は、この環境では保存できない可能性がある。#4 の約 397 MB は収まるので、#4 の失敗の原因ではない。
- iPhone の #4 の失敗の原因は、特定できていない。wllama のコードには、JSPI(`WebAssembly.Suspending`)が無い環境で、互換ビルド(別の wasm とワーカーを CDN から取る)を使う処理がある。iPhone がそうかは、診断ページ(下の節)の `jspi` で分かる。ほかに、ワーカーの起動、OPFS、`WebAssembly.Memory` の確保、WebGPU の初期化、取得先への接続(CORS を含む)が候補で、診断ページが 1 つずつ試す。
- #6 は、モデルの読み込みは成功したが、最初の生成で wllama が abort し(`common_chat_templates_get_caps` ← `oaicompat_chat_params_parse`)、以降は「クラッシュ済み」で全件失敗した。`jinja=0&chat_template=chatml` を付けても、同じ abort で 3 回続けて失敗して止まった。診断を足して測り直すと、llama.cpp は `b11364-46ca246`、`getChatTemplate()` は空だった。**wllama から見て、この GGUF にはチャットテンプレートが無い**(診断の初版は「無い」と「空」を区別していなかったので、`null` と書くよう直した)。チャットテンプレートを要求する経路(`createChatCompletion`)がテンプレートの無いモデルで落ちる、という説明が付くが、llama.cpp の内部で確かめたわけではない。モデルが動かないと決めるのは早い。
- 生のプロンプトで生成する経路(`prompt_format=chatml`、wllama の `createCompletion`)を足した。チャットテンプレートを通らない。**LFM3 の本来のプロンプト形式は確かめていない。** ChatML 風の形式で測ると、形式が違う場合に LFM3 の質を低く測るので、この経路の結果は LFM3 の評価の結論には使わないと決めていた。
- その経路でも失敗した: `RangeError: Invalid typed array length: 1163217991`。この数値は 16 進で `0x45554c47`、ASCII で `GLUE` で、wllama の JS と wasm の間のメッセージの先頭の印である。wllama のワーカーは、出力の長さを入力バッファの先頭 4 バイトから読む(`llama-cpp.js` の `runAction`)。ネイティブの処理が長さを書かずに戻ると、先頭の印が長さとして読まれる。**生のプロンプトの経路でも、ネイティブ側が出力を返せずに失敗している**とみられる。原因を示すメッセージは JS に出ないので、特定できていない。#6 は、wllama 3.8.1(llama.cpp `b11364-46ca246`)では、どちらの経路でも生成できなかった。

## 観察(途中)

端末 A の WASM の 1 回の計測に限った事実と、そこから言えること。

事実:

| 項目 | #1 transformers.js Qwen3-0.6B | #4 wllama Qwen3-0.6B | #5 wllama Qwen3-1.7B |
| --- | --- | --- | --- |
| 毎秒のトークン数(中央値) | 1.7 | 8.8 | 4.0 |
| 最初のトークンまで(中央値、秒) | 6.1 | 2.1 | 4.9 |
| 14 件のうち、形式が有効 | 14 | 8 | 9 |
| 無効の理由 | なし | 候補が文字列でなくオブジェクト(`{"投稿": …}`)6 件 | オブジェクト(`{"text": …}`)4 件、末尾のカンマ 1 件 |
| 有効な出力のうち、3 つの候補がすべて同一 | 4 | 2 | 3 |
| 有効な出力のうち、候補に同じ文が含まれる | 11 | 3 | 4 |
| 既知の攻撃語が候補に残る(目安) | 3 件(むかつく、ふざけるな、消えろ) | 3 件(ふざけるな、バカ、消えろ) | 3 件(バカ、無能、消えろ) |

- 暴言のトピックの出力に、原文をほぼそのまま繰り返すものがある。例: #4 の「政治家は全員バカだ」と「電車で割り込まれた、ふざけるな」、#1 の「あいつだけは絶対に許さない」(攻撃語の目安には出ない)。#1 には、トピックの意図から外れた文もある(「隣人の騒音にキレそう」に「声が他人に聞こえるように注意して」)。
- この出力の質は、採点していない。上は目視の観察で、採点の代わりにならない。

言えること(端末 1 台、WASM、単一スレッド、貪欲法の範囲):

- 0.6B で、wllama(GGUF の Q4_K_M)は transformers.js(ONNX の q4)より、速く(約 5 倍)、小さく(397 MB 対 928 MB)、読み込みも短い(13.9 秒対 46.0 秒)。ただし量子化の方式が違い、同じ条件の比較ではない。
- 提案した判断の基準(有効な出力 12/14 以上)を通るのは #1 だけだが、#1 の出力は繰り返しが多く、内容が崩れたものもある。**有効な出力の数は、候補の質の基準として弱い。**
- 3 つの構成とも、暴言を穏当にする目的を安定して満たしているとは言えない。0.6B と 1.7B の差は、1.7B の方が文として整う例があるが、原文の繰り返しと攻撃語の残りは 1.7B でも出る。
- transformers.js の WASM は、端末 A では 0.6B(#1)しか動かなかった。1.7B(#2)は大きさで、LFM3(#3)は演算の未実装で、読み込みに失敗した。wllama(GGUF)は 1.7B(#5)が動いた。大きいモデルを評価に加える場合、WASM では wllama の方が現実的にみえるが、WebGPU の結果を見るまで確かなことは言えない。
- LFM3 は、2 つの経路(transformers.js の ONNX、wllama の GGUF)のどちらでも、WASM では動いていない。モデルの品質は未評価である。失敗の理由はどちらもランタイム側(未実装の演算、ネイティブの失敗)で、モデルの能力を示さない。
- 形式の失敗(オブジェクトや末尾のカンマ)は、モデルの能力よりも、出力の指定の仕方で減らせる可能性がある。wllama の型定義には、JSON スキーマで出力を制約する指定(`response_format`)がある。効くかは試していない。

出力そのもの(14 件 × 構成)は、結果の表とは別に、このリポジトリの外か、Issue のコメントに貼る。

## 確かめられていないこと

- WebGPU の経路。端末 A はアダプターがあるが、計測していない。ここまでの数値はすべて WASM である。
- マルチスレッドの WASM(`--isolation require-corp`)。
- スマートフォンでの動作。#3(WebGPU)と #4(WASM)を iPhone で試したが、どちらも読み込みで失敗した。#4 の失敗の原因は未特定で、診断ページの結果を待っている。動作の測定は未。
- #2 と #3 を WebGPU で動かせるか。#3 を別の量子化(`dtype=q8`)で WASM で動かせるか。#2 のダウンロード量。
- #6 の失敗の原因。2 つの経路とも失敗した。ネイティブのログ(DevTools のコンソール)が手がかり。LFM3 本来のプロンプト形式。
- 候補の質の採点(穏当さ、意味、自然さ、違い)。メモリの実測。2 回目の読み込み時間。
- LFM3 のライセンスの条件。日本語への対応は、一次情報では確認できず、人間の確認(2026-11-04)による。
- MediaPipe の LLM Inference の文書(`ai.google.dev`)に到達できない。
- 道具そのものの限界。GPU のメモリは測れない。回線の速さは測らない。ブラウザの内部のキャッシュの状態は、ストレージの使用量の増分で推し量るだけである。
