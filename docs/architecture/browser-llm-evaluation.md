# ブラウザ内 LLM の評価の手順

[ADR-0012](../adr/0012-browser-llm-runtime.md) の計測の手順と、結果の記録。ランタイムとモデルを決めるための、人間が自分の端末で実行できる手順を書く([Issue #16](https://github.com/asuka1975/censored/issues/16))。

**結果の欄は、まだ空である。** 作成した環境では、モデルの置き場(`huggingface.co`、`cdn-lfs.huggingface.co`)と `cdn.jsdelivr.net` へ接続できず(ネットワーク方針が 403 で拒否)、GPU も無いため、計測できなかった。計測の道具は [`tools/llm-bench/`](../../tools/llm-bench/) に用意した。人間が自分の端末で動かし、結果を返す([計測の手順](#計測の手順))。

作成した環境で確かめたのは、道具の側だけである。判定と集計の純粋な関数と配信のテストが通ること、偽のライブラリを差し込んだヘッドレス Chromium でページが最後まで動くこと。**ライブラリの実物とモデルは、一度も動かしていない。**

## 評価する構成

| # | ランタイム | モデル(量子化) | 経路 | 備考 |
| --- | --- | --- | --- | --- |
| 1 | transformers.js | Qwen3-0.6B(ONNX、q4) | WebGPU、WASM | 小さいモデルの基準 |
| 2 | transformers.js | Qwen3-1.7B(ONNX、q4) | WebGPU、WASM | |
| 3 | transformers.js | LFM3-1.7B(ONNX、q4) | WebGPU、WASM | #2 と同じ大きさの比較 |
| 4 | wllama | Qwen3-0.6B(GGUF、Q4_K_M) | WebGPU、WASM | |
| 5 | wllama | Qwen3-1.7B(GGUF、Q4_K_M) | WebGPU、WASM | |
| 6 | wllama | LFM3-1.7B(GGUF、Q4_K_M) | WebGPU、WASM | llama.cpp と wllama が LFM3 に対応するか未確認。GGUF が無い、または動かなければ、動かなかったと記録して省く |

モデルの選び方:

- 比べるモデルは Qwen3 と LFM3(人間の指示、2026-11-04)。Gemma は外した。
- Qwen3 は、公式の README が Apache 2.0 と書く。小型版(0.6B、1.7B)を使う。
- LFM3 は、Liquid の公式リポジトリ(cookbook)に `LFM3-1.7B` が出てくる。transformers.js の対応モデルに載る。`LFM3-1.7B` が日本語に対応することは、人間が確認した(2026-11-04)。ライセンスの条件は、確かめていない。**使う前に、人間が確認する。**
- ONNX と GGUF の配布の有無と、実際の大きさは、確かめていない。見つからないモデルは、別の同程度のモデルに替えて、記録する。
- WebLLM は、WebGPU でしか動かないので、基盤の候補にも、計測の対象にも含めない。

## 計測の手順

構成 1 つと経路 1 つを、ブラウザのページ 1 枚で測る。ページが時間、ダウンロード量、出力の判定を自動で記録する。人間が行うのは、サーバーの起動、キャッシュの消去、メモリの読み取り、採点、結果を返すことである。

### 準備

- Node.js 22 以上。リポジトリの依存の導入は要らない(ライブラリは版を固定して CDN から取る。transformers.js 4.3.2、wllama 3.8.1)。
- Chrome か Edge(WebGPU の経路は 113 以降)。`huggingface.co`、`cdn-lfs.huggingface.co`、`cdn.jsdelivr.net` に接続できること。
- 取得先のモデルの名前は、**#1 以外は推測である**。最初に、次の表の名前が `huggingface.co` に実在するか確かめる。無ければ、似たモデルを探して `repo=`(必要なら `file=`)で差し替え、使った名前を結果に書く。

| # | 既定の取得先 | 確認 |
| --- | --- | --- |
| 1 | `onnx-community/Qwen3-0.6B-ONNX` | transformers.js の例にある名前。存在は未確認 |
| 2 | `onnx-community/Qwen3-1.7B-ONNX` | 推測 |
| 3 | `onnx-community/LFM3-1.7B-ONNX` | 推測。無ければ Liquid AI の公式の取得先を探す |
| 4 | `unsloth/Qwen3-0.6B-GGUF`(Q4_K_M) | 推測 |
| 5 | `unsloth/Qwen3-1.7B-GGUF`(Q4_K_M) | 推測 |
| 6 | `LiquidAI/LFM3-1.7B-GGUF`(Q4_K_M) | 推測。llama.cpp が LFM3 に対応していないと、読み込みで失敗する(失敗も結果である) |

### 1 つの構成を測る

1. サーバーを起動する。`--isolation` は後述。

   ```bash
   node tools/llm-bench/serve.mjs --port 8080
   ```

2. **冷間(初回)の測定。** 開発者ツールの Application の Storage で「Clear site data」を押す。次の URL を開いて「計測を始める」を押す。`config` は上の表の #、`backend` は `webgpu` か `wasm`。

   ```text
   http://localhost:8080/?config=1&backend=wasm&cache=cold
   ```

   14 件すべてを 1 回ずつ生成する。終わるまで待つ(WASM の大きいモデルは数十分かかりうる)。生成中に Chrome のタスクマネージャー(Shift+Esc)でこのタブの「メモリ フットプリント」を読み、「タスクマネージャーのタブのメモリ」に入れる。出力の採点は任意(下の「採点」を見る)。
3. 「全体を JSON で保存」を押し、ファイルを残す。「要約をコピー」で、要約をコピーする。
4. **温間(2 回目)の測定。** キャッシュを残したまま、次の URL を開いて同じ操作をする。2 回目の読み込み時間と、生成の時間の中央値(3 トピック × 3 回 = 9 回)が取れる。

   ```text
   http://localhost:8080/?config=1&backend=wasm&cache=warm&topics=1,3,13&reps=3
   ```

5. 手順 2〜4 を、ほかの構成と経路で繰り返す。

全部を測れなくてよい。先に #1 と #3(最も小さいモデルと LFM3)を WebGPU と WASM で測り、桁を見る。次に #2、そして wllama(#4〜#6)。最後に、残った候補を中程度のスマートフォンで測る。

### 注意

- **冷間が冷間でないとき。** 要約の `load.storageDeltaBytes` が 0 に近ければ、キャッシュが残っていた。「Clear site data」で消えなかったので、新しいプロファイルで測り直す。
- **WebGPU の経路。** 使えない端末では、ページは「アダプターを取得できない」と表示して止まる。WASM に黙って落とすことはしない。
- **wllama のマルチスレッド。** `--isolation require-corp`(または `credentialless`)でサーバーを起動した測定と、起動しない測定の両方を取る。結果の `env.crossOriginIsolated` で見分けられる。ヘッダーを付けると、CDN からの読み込みが拒否されて失敗することがある。失敗したら、そのまま報告する。
- **生成は貪欲法(temperature=0)。** 再現するため。繰り返しの出力で無効が増えたら、サンプリングを足して測り直し、設定を書く(例: `temperature=0.7&top_p=0.8&top_k=20`。Qwen3 のモデルカードの推奨値を覚えているものだが、ここでは確かめていない。LFM3 の推奨値はモデルカードで確かめる)。
- **量子化の指定。** transformers.js の `dtype` は q4 が既定。WebGPU で `shader-f16` が使える端末(結果の `env.adapter.shaderF16`)では、`dtype=q4f16` も測る価値がある。wllama は `quant=Q4_K_M` が既定。
- **Qwen3 の思考。** Qwen3 の構成は、利用者の発言の末尾に `/no_think` を付けて思考を止める。LFM3 には付けない。それでも `<think>` が出たときは取り除いて判定し、`hadThinking` に記録する。
- **スマートフォン。** Android の Chrome なら、USB デバッグで `adb reverse tcp:8080 tcp:8080` をして `http://localhost:8080` を開く(localhost は安全なコンテキストなので WebGPU が使える。この手順は未確認)。iPhone で使える手軽な方法は用意していない。

### 結果を返す

- 構成と経路ごとに「要約をコピー」した JSON を、そのまま貼る(1〜2 KB)。端末の説明(CPU、GPU、メモリ、OS、回線の速さ)を一言添える。
- 全体の JSON(各出力を含む)は、候補の質を見る必要がある構成だけ、Issue のコメントか、リポジトリの外に置いた場所に貼る。このリポジトリには入れない。

### 採点

ページの表に、出力ごとの 4 つの観点を 1〜5 で入れられる。入れた値は要約の平均に反映される。全構成の全件を採点するのは重いので、有効な出力が 12 件以上あった構成だけを採点してよい。「攻撃的な語が残る可能性」の印は、既知の罵倒語が候補に含まれるかを見ただけの目安で、採点の代わりにはならない。

## プロンプトの草案

実装(#15)で見直す草案。計測では、すべての構成に同じプロンプトを使う。

```text
あなたは、投稿を穏当な日本語に整えるアシスタントです。
利用者が言いたいこと(トピック)を受け取り、同じ主張の核を保ったまま、攻撃的な言葉や人格への攻撃を避けた、短い投稿文を 3 つ作ります。
- 各投稿は 140 文字以内にする。
- 3 つの投稿は、言い回しを変える。
- 罵倒、差別、個人への攻撃は書かない。
- 返信先の投稿が与えられたときは、その内容に応える投稿にする。
- 出力は、文字列 3 つの JSON の配列だけにする。
```

## 計測の方法

1 つの構成と 1 つの経路ごとに、次を記録する。自動の項目はページが記録し、手動の項目は人間が入れる。

| 項目 | 方法 |
| --- | --- |
| 端末 | 自動(ブラウザの版、論理コア数、`navigator.gpu` の有無、アダプターの情報、cross-origin isolation の有無)。CPU、GPU、メモリ、OS は手動でメモに書く |
| ダウンロードの大きさ | 自動。ランタイムが報告する転送量(`load.downloadedBytes`、`totalBytes`)と、ストレージの使用量の増分(`load.storageDeltaBytes`) |
| 初回の読み込み時間 | 自動。`cache=cold` のとき、読み込みを始めてから生成できる状態になるまで(`load.loadSeconds`)。回線の速さは手動でメモに書く |
| 2 回目以降の読み込み時間 | 自動。`cache=warm` のとき、同じ時間 |
| 生成の時間 | 自動。最初のトークンまで(`summary.medianTtftSeconds`)と、3 つの候補を得るまで(`summary.medianTotalSeconds`)の中央値。最初の 1 回(シェーダーのコンパイルを含みうる)は `summary.firstRunSeconds` に別に出し、中央値に入れない。毎秒のトークン数は `summary.medianTokensPerSecond`(wllama は 1 チャンクを 1 トークンとみなす) |
| メモリ | 手動。ブラウザのタスクマネージャーで、生成中のタブのメモリ(MB)を読む。ページが取れる値(`memory.*`)は JavaScript のヒープなどに限られ、GPU のメモリを含まないので、代わりにならない |
| 有効な出力の割合 | 自動。14 件のうち、JSON の配列として解釈でき、空でない文字列がちょうど 3 つで、各 140 書記素以内だった件数(`summary.validTopics`)。ICU 相当の `Intl.Segmenter` で数える |
| 候補の質 | 人間が採点する(上の「採点」)。出力そのものも記録する |

端末は、少なくとも次の 3 種類を測る。

1. WebGPU を使える、GPU のある端末(デスクトップ)
2. WebGPU を使えない、または使わない、CPU だけの端末(WASM の経路)
3. 利用者の想定に近い、中程度のスマートフォン

## 候補の質の採点

各出力(3 つの候補)を、人間が 1〜5 で採点する。

| 観点 | 5 の基準 | 1 の基準 |
| --- | --- | --- |
| 穏当さ | 攻撃的な言葉も、人格への攻撃も無い | 罵倒がそのまま残る |
| 意味の保持 | トピックの主張の核が残っている | 別の話になっている |
| 日本語の自然さ | そのまま投稿できる | 文法が崩れている、意味が通らない |
| 3 つの違い | 言い回しが明確に違う | ほぼ同じ文 |

返信(#13、#14)は、返信先の投稿に応える内容かも見る。

## 作成した環境で確かめられなかったこと

- モデルの重みを取得できない(`huggingface.co`、`cdn-lfs.huggingface.co`、`cdn.jsdelivr.net` が 403)。上の計測のすべてが、これに依存する。
- ライブラリの実物を一度も動かしていない。道具が呼ぶ API は、公開されたパッケージ(transformers.js 4.3.2、wllama 3.8.1)の型定義と README で確かめたもので、実行では確かめていない。ページの動作の確認には、同じ形の偽のライブラリを使った。
- モデルの取得先の名前。#1 以外は推測である(上の表)。
- GPU が無く、WebGPU の計測ができない。
- LFM3 のライセンスの条件、llama.cpp と wllama の LFM3 への対応を、一次情報で確認できない。日本語への対応は、一次情報では確認できず、人間の確認(2026-11-04)による。
- MediaPipe の LLM Inference の文書(`ai.google.dev`)に到達できない。
- 道具そのものの限界。GPU のメモリは測れない。回線の速さは測らない。ブラウザの内部のキャッシュの状態は、ストレージの使用量の増分で推し量るだけである。
