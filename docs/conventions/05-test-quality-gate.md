# テスト品質レビューゲート

テストはこのプロジェクトの **WHAT の正本** である。テストが弱いと、AI が実装を変えても誰も気づけない。判断の根拠は [ADR-0004](../adr/0004-test-stack-and-mutation.md)。

## テストの書き方

- **テスト名は仕様の一文。** 条件と結果を書く。`501文字の本文を拒否する`。`mkPostBody のテスト`、`正常系` は不可。
- **観察できる振る舞いを検証する。** 内部関数の呼び出し回数ではなく、結果と状態を見る。
- **純粋なロジックにはプロパティテストを使う**(Haskell は hedgehog、PureScript は quickcheck)。ラウンドトリップ、冪等性、不変条件は例示より強い。
- **境界値を例示で固定する。** 500 文字と 501 文字の両方。
- **外部依存はフェイクで置き換える。** フェイクは本物と同じ契約テストを通す。
- **時刻と乱数は注入する。** 実時刻の読み取りと待機は禁止。

| 層 | 主なテスト | ツール |
| --- | --- | --- |
| domain / core | プロパティ + 境界値の例示 | sydtest + hedgehog / spec + quickcheck |
| application | フェイクの Port によるユースケース | sydtest |
| contract | JSON の golden、両言語のデコード | sydtest、spec |
| infra | 実 DB での統合テスト | sydtest |
| server | HTTP レベル、特に認可 | sydtest |
| ui | 状態遷移と表示の分岐 | spec |

## 機械検査

| ID | 規則 | 検査 |
| --- | --- | --- |
| TQ-M1 | テスト名は振る舞いを述べる(曖昧な語と短すぎる名前を拒否) | `check-source` |
| TQ-M2 | `xit`、`pending`、`itOnly` などでテストを無効化しない(テストフレームワークの別名で修飾しても同じ)。`pendingWith` は理由に Issue 番号を含める場合のみ | `check-source` |
| TQ-M3 | `flaky` による再試行を禁止する。不安定なテストは原因を直す | `check-source` |
| TQ-M4 | 同じファイル内でテスト名を重複させない | `check-source` |
| TQ-M5 | テストで待機や実時刻の読み取りをしない。不可避なら直上に `WHY NOT:` | `check-source` |
| TQ-M6 | **PR の変更箇所でミュータントを生存させない**(未到達も不合格) | `hs-mutation`、`ps-mutation` |
| TQ-M7 | 全体のミューテーションスコアの下限(Haskell 80%、PureScript 70%) | 夜間ジョブ |
| TQ-M8 | 計測の健全性。ミューテーション 0 件での合格、空のマニフェスト、欠けたソースマップ、すべて判定不能の結果を不合格にする | `hs-mutation`、`ps-mutation` |
| TQ-M9 | テストの削除・改名は PR 本文に `Test-Removal: 理由` がなければ不合格 | `check-pr` |
| TQ-M10 | 計測対象外の層のソースを変更した PR は、ゲートの「対象なし」を合格の根拠にしない。ゲートが変更を通知し、レビュー AI が手作業の変異で判定する(下記) | `hs-mutation`・`ps-mutation`(通知)、レビュー |

### ミューテーションの実行

```bash
make mutation-diff   # PR の変更箇所のみ(BASE=origin/main)
make mutation-full   # 全体
```

対象は純粋層と application(`tools/policy/mutation.json`)。IO が中心の層は実行コストと誤検出が大きいので対象にしない。

ミュータントが生存したら、次の順に判断する。

1. **テストが足りない** → テストを足す。最も多い
2. **そのコードが不要** → 消す(例: 結果を変えない条件分岐)
3. **等価ミュータント**(動作が変わらない変異) → 無効化する。直上に `WHY NOT:` を書く

```haskell
-- WHY NOT: ログ文言はテストで固定しない。運用で変わる文字列をテストに持ち込むと変更のたびに壊れる。
{-# ANN notify ("DisableMutationsFor logLine" :: String) #-}
```

### 計測対象外の層(TQ-M10)

計測するのは `tools/policy/mutation.json` の層だけである。それ以外の層(infra など)のソースだけを変更した PR は、`make mutation-diff` が「対象なし」で終わり、TQ-M6 と TQ-M8 は何も保証しない。ゲートは `計測対象外の層の変更: ...` と通知する。この通知が出たら、レビュー AI は次の手順で判定する。

1. HEAD を別の場所に展開し、変更した束縛に変異を入れる(演算子の反転、定数の置換、条件の反転、呼び出しの削除など)。作業ツリーは変更しない。
2. 変異ごとに、テストが落ちるか(検出)、通るか(生存)を記録する。
3. 生存したものは、テストの不足か、不要なコードか、等価かを判断する。等価なら理由を示す。
4. 結果を TQ-M6 の根拠に書く(試した数、検出、生存と理由)。非等価の生存があるか、変異を 1 件も試せなければ `fail` にする。TQ-M8 は、手作業でも 0 件のときだけ `fail` にする。

この判定は計測の代わりにはならない。層を計測対象にするかどうかは `tools/policy/mutation.json` の判断で、ゲートの変更として別の PR で行う。

### 検証で判明した注意点

- **ビルドキャッシュが効くと、プラグインはマニフェストを書かない。** 消すと「0 件で合格」になる。`hs-mutation` はマニフェストをビルド成果物と同じ場所に保持し、空なら失敗させる。
- **テストスイート名はパッケージをまたいで一意にする**(DIR-4)。
- **UTF-8 ロケールが必須である。** POSIX ロケールでは日本語のテスト名が子プロセスの引数で壊れ、`no valid coverage-child test id` で失敗する。`make` と `hs-mutation` は `C.UTF-8` を設定する。
- **PureScript の Stryker のスコアはそのまま使わない。** 出力 JS には `derive` の実装など作者が書いていないコードが含まれる。`ps-mutation` は PS の行へ戻せて、かつ宣言行でないものだけを数える。

## レビュー観点

`test-quality-reviewer` が差分に対して判定する。機械検査では見えないものを見る。

| ID | 観点 | 不合格の例 |
| --- | --- | --- |
| TQ-R1 | 受け入れ条件がテストに対応している | PR の表に載った条件に対応するテストが無い |
| TQ-R2 | テストが実装ではなく振る舞いに結合している | リファクタリングで壊れる、内部関数の呼び出し順を検証 |
| TQ-R3 | 期待値が独立している | 実装と同じ計算で期待値を作っている(トートロジー) |
| TQ-R4 | 失敗経路と境界を覆っている | 成功の例だけ。空、上限、重複、権限なしが無い |
| TQ-R5 | プロパティの生成器が十分に広い | 生成範囲が狭く、境界に届かない |
| TQ-R6 | テストが独立している | 順序依存、共有状態 |
| TQ-R7 | Golden の更新に理由がある | 期待値を出力に合わせて貼り替えただけ |
| TQ-R8 | テストを実装に合わせて緩めていない | 既存テストの期待値が理由なく変わっている |
| TQ-R9 | フェイクが本物と乖離していない | 本物だけが返すエラーをフェイクが返さない |

TQ-R3、TQ-R7、TQ-R8 は AI が特に陥りやすい。**テストが落ちたとき、テストを直してよいのは仕様が変わったときだけである。**

## 記録

[非機能要件ゲート](04-nfr-gate.md)と同じ形式で `gate:test-quality` を PR 本文に記録する。

```markdown
<!-- gate:test-quality sha=<HEADの40桁> verdict=pass reviewer=test-quality-reviewer -->
| ID | 判定 | 根拠 |
| --- | --- | --- |
| TQ-M6 | pass | make mutation-diff: killed 12 / survived 0 |
| TQ-R3 | pass | 期待値はリテラル。`Censored/Domain/PostSpec.hs:20` |
```
