# 情報配置の原則

同じ情報を二か所に書くと、片方が必ず嘘になる。問いごとに置き場所を一つに決める。

## 置き場所の表

| 置き場所 | 答える問い | 書かないこと | 腐敗を防ぐもの |
| --- | --- | --- | --- |
| **コード** | HOW どう実現するか | 理由、経緯 | コンパイラ、テスト |
| **型** | WHAT CANNOT 何が起こり得ないか | — | コンパイラ |
| **テスト** | WHAT 何を保証するか | 実装の手順 | 実行、ミューテーション |
| **コミットログ** | WHY なぜ今この変更か | 変更内容の逐語説明 | 不変(履歴) |
| **コメント** | WHY NOT なぜ自明な別解を採らないか | HOW、WHAT、経緯 | `check-source`、レビュー |
| **ADR** | WHY THIS なぜこの設計か(代替案と却下理由) | 実装の詳細 | 不変(`check-adr`) |
| **プロダクト文書** | WHAT FOR 誰のために何を実現するか | 実現方法 | 定期レビュー |
| **NFR カタログ** | HOW WELL どの水準で動くべきか | 実現方法 | レビューゲート |
| **Runbook** | WHAT IF 何か起きたらどうするか | 設計の理由 | 訓練、定期レビュー |
| **AGENTS.md / 規約** | HOW TO WORK どう作業するか | プロダクト固有の知識 | ゲート |

## 迷ったときの判定

1. **型で表現できるか** → 型にする。文章にしない。
2. **実行して確かめられるか** → テストにする。
3. **この変更をしなければ生まれなかった理由か** → コミットログ。
4. **将来の変更者が同じ別解を試して失敗しそうか** → コメントに WHY NOT。
5. **複数のモジュールや将来の判断を縛るか** → ADR。コメントとコミットからは番号で参照する。
6. **どれにも当たらないなら** → 書かない。書くべき文書を増やす前に、本当に必要か疑う。

## 紛らわしい境界

### WHY(コミット)と WHY THIS(ADR)

コミットの `Why:` はその変更に閉じた理由を書く。理由が他の変更の判断を縛るなら ADR に昇格し、コミットは `ADR: 0007` で参照する。

### WHY NOT(コメント)と WHY THIS(ADR)

一箇所で完結する別解の却下はコメント。構造に関わる別解の却下は ADR に書き、コメントは番号だけを指す。

```haskell
-- WHY NOT: ここで全件取得しない。フォロー数の上限がなく、1 リクエストで主メモリを使い切る(ADR-0012)。
```

### Haddock はコメントの例外

Haddock は読み手が実装を開かずに使うための API 契約なので、WHY NOT の規則の例外として認める。ただし書けるのは次だけとする([07 コメント](07-comments.md))。

- モジュールの責務(必須、1〜3 行)
- 型で表せない事前条件・事後条件・法則

処理手順は書かない。手順を書きたくなったら、関数を分割して名前で表す。

## ゲートの原則

- **機械で判定できる規則は機械で判定する。** 文章だけの規則は AI にも人にも守られない。
- **ゲートは手元で再現できる。** CI 固有のチェックを作らず `make` に集約する。
- **ルールには ID を振る。** 違反の報告とレビュー指摘は ID を引用する(`check-source` の `[CMT-1]` など)。
- **抑止には理由を要求する。** `-Wno-`、`HLINT ignore`、`DisableMutation` は直上の `WHY NOT:` なしに通らない。
- **ゲートの緩和は製品コードと別の PR にする**([AI-8](11-ai-native-flow.md))。
- **偽の合格を最も警戒する。** 不合格は気づけるが、誤った合格は誰も調べない。計測が機能していないことを検出する検査(`COV-2`、`TQ-M8`)を計測そのものと同等に扱う。
- **検査の前提が満たされないときは合格にしない(`GATE-1`)。** 解釈できない設定、見つからないビルド計画、欠けたソースマップは、問題なしではなく「判定できない」である。読み飛ばさず失敗させる。
