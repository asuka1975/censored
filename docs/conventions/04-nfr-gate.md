# 非機能要件レビューゲート

機能のテストは「動くこと」しか保証しない。SNS の事故の多くは、動いているのに他人の投稿が見える、一人のフォロー数で DB が止まる、退会後もデータが残る、といった非機能の問題である。

要件そのものは [NFR カタログ](../nfr/catalog.md) に置く。この文書は確認の手順を定める。記録方式の根拠は [ADR-0008](../adr/0008-review-gate-record.md)。

## 流れ

```text
1. 変更パスから観点を選ぶ   カタログの「変更パスと観点の対応」
2. 独立したレビュアーが判定  nfr-reviewer(作成者の文脈を持たない)
3. 判定を PR 本文に記録     /review-gates が追記
4. CI が記録の鮮度を検証    pr-policy(sha が HEAD と一致し verdict=pass。本文の編集でも再実行)
5. 人間が記録を読んで承認   必須
```

## 規則

| ID | 規則 | 検査 |
| --- | --- | --- |
| NG-1 | 製品コードを変更する PR には、HEAD に対する `gate:nfr` の記録が必要 | `check-pr` |
| NG-2 | レビュアーは作成者と別のコンテキストで動かす。作成時の思考や会話を渡さない | 手順、スキル |
| NG-3 | 判定は NFR ID ごとに `pass` / `fail` / `n/a` と根拠(ファイル:行、テスト名、計測値)を示す。根拠のない `pass` は無効 | レビュー |
| NG-4 | `fail` が 1 件でもあれば全体が `fail`。例外は人間が ADR または Issue で受け入れた場合のみ | レビュー |
| NG-5 | 数値要件は可能な限り CI の自動検査に移す。移した項目はカタログの検証方法を更新する | カタログ |
| NG-6 | 新しい種類の障害が起きたらカタログに項目を追加する | [AI-11](11-ai-native-flow.md) |
| NG-7 | 閾値の変更は人間が承認する | CODEOWNERS |

## 判定の対象

レビュアーは変更差分とその周辺だけを読む。リポジトリ全体の監査はしない。**差分に現れない要件違反も見る。** 例えば新しいエンドポイントの追加では、差分に認可の処理が **無いこと** が指摘の対象になる。

## 記録の形式

```markdown
<!-- gate:nfr sha=<HEADの40桁> verdict=pass reviewer=nfr-reviewer -->
| NFR ID | 判定 | 根拠 |
| --- | --- | --- |
| NFR-SEC-2 | pass | `Censored.Server.Handler.Post:42` で所有者を確認。`他人の投稿を削除できない` テストあり |
| NFR-PERF-3 | pass | `listTimeline` はカーソル必須で上限 50 件 |
| NFR-PRIV-1 | n/a | 個人情報を扱う経路の変更なし |
```

HEAD が変わると記録は無効になる。リベース後も再実行する。基準ブランチが変われば判定の前提も変わり得るため。

## このゲートの限界

- 記録は PR 本文の文字列なので **偽造を技術的には防げない**。防ぐのは人間の承認である。承認者はレビュー記録が実際の差分に対応しているかを見る。
- AI の判定は網羅性を保証しない。認証・認可・個人情報に関わる変更(リスク区分 C)は人間が全行を読む。
- 負荷に関する判定は静的な読解に留まる。実測は負荷試験で行う。
